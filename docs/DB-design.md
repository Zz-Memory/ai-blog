# 第4章  数据库设计

## 4.1  数据库需求分析

本项目是一个基于 `Next.js + Prisma + PostgreSQL` 构建的 AI 辅助个人博客系统，围绕“内容创作、内容发布、文章阅读、互动交流、AI 辅助”五个核心场景展开。系统的数据库设计需要同时满足博主端和访客端的业务需求，并为登录认证、文章管理、评论互动、点赞收藏、浏览历史、站内通知以及 AI 问答等功能提供稳定的数据支撑。

从业务对象来看，系统的基础对象主要包括用户、文章、分类、标签、评论、点赞、收藏、浏览历史、通知以及 AI 问答会话等。其中，用户分为博主和访客两种角色，博主主要负责文章的创作、编辑、发布与内容管理，访客主要负责浏览文章、发表评论、点赞收藏和参与 AI 问答。为了实现账号体系和会话管理，系统还需要建立会话表和验证码表，以支撑登录、注册、重置密码等认证流程。

从内容管理需求来看，系统需要对文章的草稿状态和发布状态进行统一管理。文章不仅要保存标题、摘要、正文 Markdown 内容、HTML 内容，还要记录作者、所属分类、发布时间、创建时间和更新时间等信息。由于文章详情页支持分类筛选、标签筛选与站内搜索，因此还需要设计分类表、标签表以及文章标签关联表，用于维护文章与分类、标签之间的关系。

从互动需求来看，系统需要记录用户在文章上的评论、回复、点赞、收藏和浏览行为。评论功能不仅要支持用户对文章发表评论，还要支持评论回复和评论审核，因此需要评论表来保存评论内容、评论状态、父评论关系等信息。点赞和收藏功能需要通过独立的数据表记录用户与文章之间的关联关系，并通过唯一约束避免重复操作。浏览历史则用于记录用户访问过的文章，便于在个人中心中展示最近阅读记录。

从消息通知需求来看，系统需要为评论提醒、系统广播等场景提供站内通知能力。通知数据不仅要记录接收者、发送者、通知类型、标题、内容、跳转链接、已读状态和创建时间，还要支持用户在个人中心或博主中心查看通知列表。这样可以保证用户在产生互动行为后能够及时收到反馈信息。

从 AI 功能需求来看，系统在文章详情页提供 AI 问答能力，用户可以围绕当前文章与 AI 进行对话，也可以发起通用问答。为了保存对话记录并支持历史回看，需要设计 AI 问答会话表和 AI 问答消息表。会话表用于记录某个用户与某篇文章对应的一次对话上下文，消息表用于记录对话中的每一轮消息内容及角色信息。

综上所述，系统数据库设计应重点覆盖以下几类数据：

1. 用户与认证数据：用户、会话、验证码。
2. 内容管理数据：文章、分类、标签、文章标签关联。
3. 互动行为数据：评论、点赞、收藏、浏览历史。
4. 通知提醒数据：站内通知。
5. AI 对话数据：AI 问答会话、AI 问答消息。

## 4.2  数据库概念结构设计

根据系统需求分析，可以抽象出以下主要实体：用户实体、会话实体、验证码实体、文章实体、分类实体、标签实体、评论实体、点赞实体、收藏实体、浏览历史实体、通知实体、AI 问答会话实体和 AI 问答消息实体。各实体之间的关系主要包括：用户与文章的一对多关系、文章与评论的一对多关系、用户与评论的一对多关系、文章与分类的一对多关系、文章与标签的多对多关系、用户与点赞/收藏/浏览历史的一对多关系、用户与通知的一对多关系，以及用户与 AI 问答会话的一对多关系、AI 问答会话与消息的一对多关系。

### 4.2.1  用户与文章实体关系图

用户与文章之间存在“创建”关系。一个用户可以创建多篇文章，而每篇文章只能归属于一个作者。其关系如图4-1所示。

图4-1  用户与文章实体关系图

```text
用户 1 ── 创建 ── N 文章
```

### 4.2.2  文章与评论实体关系图

文章与评论之间存在“发布”关系。一篇文章可以对应多条评论，而每条评论只属于一篇文章。评论还可以形成父子嵌套关系，用于表示回复结构。其关系如图4-2所示。

图4-2  文章与评论实体关系图

```text
文章 1 ── 发布 ── N 评论
评论 1 ── 回复 ── N 回复评论
```

### 4.2.3  用户与互动行为实体关系图

用户与点赞、收藏、浏览历史之间都存在“产生”关系。一个用户可以对多篇文章点赞、收藏，并形成多条浏览历史记录。其关系如图4-3所示。

图4-3  用户与互动行为实体关系图

```text
用户 1 ── 点赞 ── N 点赞记录 ── 指向 ── 1 文章
用户 1 ── 收藏 ── N 收藏记录 ── 指向 ── 1 文章
用户 1 ── 浏览 ── N 浏览历史 ── 记录 ── 1 文章
```

### 4.2.4  用户与通知实体关系图

系统中的通知既可以由系统发送，也可以由其他用户发送。一个用户可以接收多条通知，同时也可以作为通知发送者参与多条通知。其关系如图4-4所示。

图4-4  用户与通知实体关系图

```text
用户 1 ── 接收 ── N 通知
用户 1 ── 发送 ── N 通知
```

### 4.2.5  用户与 AI 问答实体关系图

用户与 AI 问答会话之间存在“发起”关系，一个用户可以在不同文章下创建多个问答会话；每个会话中又包含多条问答消息。其关系如图4-5所示。

图4-5  用户与 AI 问答实体关系图

```text
用户 1 ── 发起 ── N AI问答会话 1 ── 包含 ── N AI问答消息
```

### 4.2.6  文章与分类、标签实体关系图

文章与分类之间为“归属”关系，一篇文章只能有一个分类；文章与标签之间为“关联”关系，一篇文章可对应多个标签，一个标签也可被多篇文章使用。其关系如图4-6所示。

图4-6  文章与分类、标签实体关系图

```text
分类 1 ── 归属 ── N 文章
文章 N ── 关联 ── N 标签
```

## 4.3  数据库逻辑结构设计

本系统采用 PostgreSQL 作为后台数据库，数据模型通过 Prisma 进行映射。依据 `prisma/schema.prisma` 中的实体定义，系统数据库的逻辑结构主要由 14 张核心表组成，分别是：`User`、`VerificationCode`、`Session`、`Post`、`Category`、`Tag`、`PostTag`、`Comment`、`Like`、`Bookmark`、`BrowseHistory`、`Notification`、`AiChatSession` 和 `AiChatMessage`。

### 4.3.1  用户信息表（`User`）

用户信息表用于存放系统登录用户的基础信息，包含博主和访客两类用户。用户账号通过邮箱和用户名进行唯一标识，密码以哈希形式存储，角色字段用于区分用户类型。

表4-1  用户信息表（`User`）

| 字段名 | 数据类型 | 数据长度 | 字段描述 | 字段说明 |
| --- | --- | --- | --- | --- |
| id | String | 64 | 用户ID，主键 | 非空 |
| email | String | 255 | 邮箱 | 非空，唯一 |
| username | String | 255 | 用户名 | 非空，唯一 |
| passwordHash | String | 255 | 密码哈希 | 非空 |
| role | UserRole | - | 用户角色 | 非空，默认 `VISITOR` |
| intro | String | - | 个人简介 | 可空 |
| status | UserStatus | - | 用户状态 | 非空，默认 `ACTIVE` |
| createdAt | DateTime | - | 创建时间 | 非空 |
| updatedAt | DateTime | - | 更新时间 | 非空 |

### 4.3.2  验证码表（`VerificationCode`）

验证码表用于存储注册、重置密码、注销账号等场景中的一次性验证码记录，便于进行邮箱验证和有效期控制。

表4-2  验证码表（`VerificationCode`）

| 字段名 | 数据类型 | 数据长度 | 字段描述 | 字段说明 |
| --- | --- | --- | --- | --- |
| id | String | 64 | 验证码ID，主键 | 非空 |
| email | String | 255 | 邮箱 | 非空 |
| code | String | 32 | 验证码内容 | 非空 |
| purpose | VerificationPurpose | - | 验证码用途 | 非空 |
| expiresAt | DateTime | - | 过期时间 | 非空 |
| consumedAt | DateTime | - | 使用时间 | 可空 |
| createdAt | DateTime | - | 创建时间 | 非空 |

### 4.3.3  会话表（`Session`）

会话表用于保存用户登录后的会话信息，通过会话令牌哈希实现登录态管理，并支持会话过期控制。

## 4.4  枚举类型设计

为了统一管理系统中的状态值和角色值，数据库在 Prisma 中定义了若干枚举类型。枚举类型能够限制字段取值范围，减少非法数据写入，同时也让业务语义更加清晰。

### 4.4.1  用户角色枚举（`UserRole`）

用户角色枚举用于区分系统中的不同用户身份，当前主要包括博主和访客两类。

表4-15  用户角色枚举（`UserRole`）

| 枚举值 | 含义 |
| --- | --- |
| BLOGGER | 博主用户，拥有文章创作、编辑、发布、评论审核等管理权限 |
| VISITOR | 访客用户，主要用于文章浏览、互动评论、收藏点赞和 AI 问答 |

### 4.4.2  用户状态枚举（`UserStatus`）

用户状态枚举用于标识账号当前是否可正常使用。

表4-16  用户状态枚举（`UserStatus`）

| 枚举值 | 含义 |
| --- | --- |
| ACTIVE | 正常状态，账号可登录并执行对应功能 |
| BANNED | 封禁状态，账号受限，不能正常使用系统 |

### 4.4.3  文章状态枚举（`PostStatus`）

文章状态枚举用于表示文章当前所处的生命周期阶段。

表4-17  文章状态枚举（`PostStatus`）

| 枚举值 | 含义 |
| --- | --- |
| DRAFT | 草稿状态，文章尚未正式发布 |
| PUBLISHED | 已发布状态，文章可在首页和详情页对外展示 |

### 4.4.4  评论状态枚举（`CommentStatus`）

评论状态枚举用于控制评论是否通过审核并对外展示。

表4-18  评论状态枚举（`CommentStatus`）

| 枚举值 | 含义 |
| --- | --- |
| PENDING | 待审核状态，评论尚未通过审核 |

### 4.4.5  通知类型枚举（`NotificationType`）

通知类型枚举用于区分不同来源和用途的站内通知。

表4-19  通知类型枚举（`NotificationType`）

| 枚举值 | 含义 |
| --- | --- |

## 4.5  数据库表之间的关系设计

结合 Prisma schema 中的实体定义，系统主要表之间的关系如下：

1. **用户与文章关系**：一个用户可以创建多篇文章，文章通过 `authorId` 关联作者，因此为一对多关系。
2. **文章与分类关系**：一个分类可以包含多篇文章，文章通过 `categoryId` 关联分类，因此为一对多关系。
3. **文章与标签关系**：文章与标签通过 `PostTag` 建立多对多关系。
4. **用户与评论关系**：一个用户可以发表多条评论，因此为一对多关系。
5. **文章与评论关系**：一篇文章可以有多条评论，因此为一对多关系。
6. **评论自关联关系**：评论通过 `parentId` 形成父子评论结构，实现楼中楼回复。
7. **用户与点赞、收藏关系**：一个用户可以对多篇文章点赞或收藏，因此为一对多关系；同时一篇文章也可被多个用户点赞或收藏。
8. **用户与浏览历史关系**：一个用户可以形成多条浏览历史记录，因此为一对多关系。
9. **用户与通知关系**：一个用户可以接收多条通知，也可以作为通知发送者，因此通过两个外键分别建立接收者关系和发送者关系。
10. **用户与 AI 问答会话关系**：一个用户可创建多个 AI 会话，一个会话对应一篇文章，因此会话与用户、文章均为多对一关系；会话与消息为一对多关系。

## 4.5  数据库设计特点

结合本项目的业务场景与 Prisma 模型定义，数据库设计具有以下几个特点：

### 4.5.1  结构清晰，职责单一

系统将用户、内容、互动、通知和 AI 对话分别拆分为独立表结构，各表职责明确，便于后续维护和功能扩展。

### 4.5.2  采用外键约束保证数据一致性

文章、评论、点赞、收藏、浏览历史、通知、会话和 AI 消息等表都通过外键与核心实体关联，避免出现孤立数据，保证数据完整性。

### 4.5.3  使用联合唯一约束防止重复记录

点赞表、收藏表采用 `userId + postId` 联合唯一约束，AI 问答会话表采用 `userId + postId` 联合唯一约束，能够有效防止重复点赞、重复收藏和重复创建会话。

### 4.5.4  索引设计满足高频查询场景

系统在文章列表、评论查询、通知列表、AI 对话历史等高频场景中配置了必要索引，例如文章作者索引、文章状态索引、评论文章索引、通知接收者索引、消息会话索引等，以提高查询效率。

### 4.5.5  支持业务流程闭环

从用户注册、登录、发布文章、发表评论，到点赞收藏、浏览记录、通知提醒和 AI 问答记录，数据库均提供了对应的数据载体，能够形成完整的业务闭环。
